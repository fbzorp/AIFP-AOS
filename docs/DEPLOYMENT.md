# Production Deployment Guide

This guide covers production deployment of AIFP-AOS including TLS setup, monitoring, automated backups, and restore procedures.

## Server / VPS Requirements

**Minimum Requirements:**
- CPU: 2 vCPU
- RAM: 4GB (recommended 8GB for production)
- Storage: 30GB (includes database, SEO pages, backups, and logs)
- Network: Public IP with ports 80 and 443 accessible
- OS: Ubuntu 22.04 LTS or equivalent

**Recommended:**
- CPU: 4 vCPU
- RAM: 8GB
- Storage: 50GB+ (for extended backup retention)
- Domain: Custom domain with DNS configured

## Production Deployment Steps

### 1. Clone and Setup

```bash
# Clone repository
git clone https://github.com/fbzorp/AIFP-AOS.git
cd AIFP-AOS

# Create production environment file
cp .env.production.example .env.production

# Edit with actual values
nano .env.production
```

### 2. Configure Environment Variables

Required variables in `.env.production`:
```bash
# Application
SECRET_KEY=your-random-secret-key-here

# Database
POSTGRES_PASSWORD=your-strong-database-password-here

# AI / LLM
DEEPSEEK_API_KEY=your-deepseek-api-key-here

# Domain (for SSL)
DOMAIN=your-domain.com
```

### 3. Deploy with Docker Compose

```bash
# Build and start all services
docker compose -f docker-compose.prod.yml up -d

# Run database migrations
docker compose -f docker-compose.prod.yml exec -T api alembic upgrade head

# Check service status
docker compose -f docker-compose.prod.yml ps
```

## SSL/TLS Configuration

### Let's Encrypt Setup

**Prerequisites:**
1. Set `DOMAIN=your-domain.com` in `.env.production`
2. Configure DNS A record pointing to your server IP
3. Ensure ports 80 and 443 are accessible from internet

**Automatic Certificate Management:**

The system includes a Certbot service that automatically:
- Obtains SSL certificates using ACME HTTP-01 challenge
- Stores certificates in `nginx/ssl/` directory
- Renews certificates every 12 hours
- Triggers Nginx reload after successful renewal

**Certificate Verification:**

After deployment, verify HTTPS works:
```bash
# Check SSL certificate
curl -I https://your-domain.com/health

# Should return HTTP/2 200 with proper SSL headers
# Test with online SSL checker: https://www.ssllabs.com/ssltest/
```

**Evidence Required:**
- [ ] Certificate issued successfully (check with `docker compose -f docker-compose.prod.yml logs certbot`)
- [ ] HTTPS accessible at `https://your-domain.com`
- [ ] SSL certificate shows valid expiration date
- [ ] No SSL warnings in browser

### Fallback to Self-Signed Certificates

For local/staging without a domain, the system falls back to self-signed certificates generated by the `cert-init` service. These are suitable for development but will show browser warnings.

## Monitoring and Alerting

### Monitoring Stack

The production deployment includes:
- **Prometheus**: Metrics collection and storage
- **Grafana**: Visualization and dashboards
- **PostgreSQL Exporter**: Database metrics
- **Redis Exporter**: Cache metrics
- **API Metrics**: FastAPI `/metrics` endpoint

### Accessing Monitoring

```bash
# Grafana (default credentials: admin/admin - change on first login)
http://your-domain.com:3000

# Prometheus
http://your-domain.com:9090
```

### Alert Configuration

Alerts are configured in Prometheus rules. Default alerts include:
- API service down
- High error rate (>5%)
- Database connection failures
- High memory usage (>80%)

**Alert Channels:**

Configure alert notification channels in `.env.production`:
```bash
# Email alerts (SMTP configuration)
ALERT_EMAIL_ENABLED=true
ALERT_EMAIL_SMTP_HOST=smtp.gmail.com
ALERT_EMAIL_SMTP_PORT=587
ALERT_EMAIL_SMTP_USER=your-email@gmail.com
ALERT_EMAIL_SMTP_PASSWORD=your-app-password
ALERT_EMAIL_TO=alerts@your-domain.com

# Telegram alerts
ALERT_TELEGRAM_ENABLED=true
ALERT_TELEGRAM_BOT_TOKEN=your-bot-token
ALERT_TELEGRAM_CHAT_ID=your-chat-id

# Webhook alerts
ALERT_WEBHOOK_ENABLED=true
ALERT_WEBHOOK_URL=https://your-webhook-url.com/alerts
```

### Test Alert Procedure

To test that alerts are working:

```bash
# Trigger a test alert (simulates service down)
docker compose -f docker-compose.prod.yml exec prometheus wget -O /dev/null http://api:8000/nonexistent-endpoint

# Check Grafana alerts panel for alert firing
# Verify alert received via configured channel (email/Telegram/webhook)
```

**Evidence Required:**
- [ ] Test alert triggered successfully
- [ ] Alert received via configured channel
- [ ] Alert shows correct information

## Automated Backups

### Backup Schedule

Automated database backups are configured to run:
- **Frequency**: Daily at 2:00 AM UTC
- **Retention**: 7 days (configurable)
- **Storage**: Local volume `backups/` with optional offsite sync

### Backup Configuration

Configure backup settings in `.env.production`:
```bash
# Backup schedule (cron format)
BACKUP_SCHEDULE="0 2 * * *"

# Retention policy (days)
BACKUP_RETENTION_DAYS=7

# Backup storage location
BACKUP_DIR=/backups
```

### Manual Backup

```bash
# Run backup manually
docker compose -f docker-compose.prod.yml exec -T api /app/scripts/backup_database.sh

# List available backups
docker compose -f docker-compose.prod.yml exec -T api ls -lh /backups/
```

### Backup Monitoring

The system monitors backup failures and triggers alerts via the monitoring stack. Check backup status:

```bash
# View backup logs
docker compose -f docker-compose.prod.yml logs backup

# Check latest backup
docker compose -f docker-compose.prod.yml exec -T api ls -lt /backups/ | head -1
```

## Restore Procedure

### Automated Restore Test

The system includes an automated restore test script:

```bash
# Run restore test
docker compose -f docker-compose.prod.yml exec -T api /app/scripts/test_restore.sh
```

This script:
1. Creates a test backup
2. Modifies a test row in the database
3. Restores from the backup
4. Verifies the test row is recovered
5. Reports success/failure

### Manual Restore

```bash
# Stop the API service
docker compose -f docker-compose.prod.yml stop api worker scheduler

# Restore from specific backup
docker compose -f docker-compose.prod.yml exec -T postgres pg_restore -U aifp -d aifp_prod /backups/backup-YYYY-MM-DD-HH-MM.dump

# Restart services
docker compose -f docker-compose.prod.yml start api worker scheduler
```

### Restore Evidence Required

After restore testing, document:
- [ ] Backup file successfully created
- [ ] Restore completed without errors
- [ ] Data integrity verified (row count matches)
- [ ] Application functionality verified post-restore

## Security Checklist

Before going live:

- [ ] Changed all default passwords in `.env.production`
- [ ] SSL certificates valid and HTTPS working
- [ ] Firewall configured (only ports 80, 443, SSH accessible)
- [ ] SSH key authentication enabled
- [ ] Fail2ban installed and configured
- [ ] Regular security updates scheduled
- [ ] CI security gates passing (pip-audit, bandit, Gitleaks)
- [ ] No secrets committed to repository

## Troubleshooting

### SSL Certificate Issues

```bash
# Check certbot logs
docker compose -f docker-compose.prod.yml logs certbot

# Manual certificate renewal
docker compose -f docker-compose.prod.yml run --rm certbot renew --force-renewal

# Check nginx SSL configuration
docker compose -f docker-compose.prod.yml exec nginx nginx -t
```

### Database Connection Issues

```bash
# Check database logs
docker compose -f docker-compose.prod.yml logs postgres

# Test database connection
docker compose -f docker-compose.prod.yml exec -T postgres pg_isready -U aifp
```

### Backup Failures

```bash
# Check backup logs
docker compose -f docker-compose.prod.yml logs backup

# Verify backup directory permissions
docker compose -f docker-compose.prod.yml exec -T api ls -la /backups/
```

## Maintenance

### Regular Maintenance Tasks

- **Daily**: Review backup logs
- **Weekly**: Review Grafana dashboards and alerts
- **Monthly**: Update Docker images and dependencies
- **Quarterly**: Review and update security policies

### Log Rotation

Logs are automatically rotated by Docker. For extended log retention, configure centralized logging (ELK stack, CloudWatch, etc.).

## Scaling

### Horizontal Scaling

For high-traffic deployments:
- Add additional API instances behind Nginx load balancer
- Configure Redis for session management
- Use external PostgreSQL with read replicas

### Database Scaling

For large datasets:
- Increase PostgreSQL resources (CPU, RAM)
- Configure connection pooling
- Consider read replicas for analytics queries
